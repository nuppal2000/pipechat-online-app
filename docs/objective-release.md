## Architecture and Security

| Boundary | Current contract |
| --- | --- |
| Browser and AI | Chat proposes structured actions. Shared validators and canonical reads produce reviewable plans; confirmed writes use version checks. Model prose, pasted material, and browser totals are not authoritative CRM facts. |
| Primary CRM and tasks | Existing records/schema/tasks retain their established storage and public RPC contracts. The new action journal records writes through its commit paths, import receipts, and conflict-checked undo. Older direct save calls are not retroactively journaled. |
| Linked business records | Migration 013 adds typed entities, stable relationships, views, scoped access, and audit history alongside primary CRM records. Primary records are referenced, not copied into the graph. Graph saves have their own version checks and audit transaction. |
| Documents | The server builds a fact bundle from the authenticated owner's current record. `POST /api/documents/proposal` previews or downloads escaped, printable HTML after checking the source version. No model-authored HTML or invented commercial terms are accepted. |
| Workflows | Typed choice-field transitions, one no-open-qualifying-task condition, and linked-task creation with an explicit timezone/calendar-day offset. Migration 016 derives events from canonical writes, rechecks conditions, and persists execution identities/history. |
| Conversations | Migration 015 preserves the 010/012 active-conversation RPCs and adds stable thread identities, full archived snapshots, and turn receipts. New/switch operations compare expected epoch/version; switching rotates the active epoch and does not revive old confirmations. |
| Telemetry | Request, plan, model, action, and undo stages are distinct. Model attempts record provider usage before parsing. Journal action/undo success events share the SQL commit transaction; request/model telemetry is not part of that same atomic transaction. |

The hosted adapter uses the **publishable/anon key plus the user's authenticated JWT**, not a service-role secret. Public data RPCs check the user and live `session_id`; private tables/helpers have restrictive grants and RLS. Trusted migration-owner access is separate from application credentials. Keep the private `pipechat` schema unexposed and never add a service key to solve an application permission problem.

Business sharing requires an existing account. Workspace roles are `viewer` and `editor`; record/view grants are read-only. Editors cannot change graph schema or sharing. Scoped reads do not traverse into unshared endpoints. These grants do not confer general legacy CRM write access or access to another user's conversations, usage, or diagnostics. Chat is blocked while the UI shows someone else's shared workspace. Sharing sends no email invitation.

Conversation RPCs intentionally retain the original owner-editable transcript model: authenticated users can write their own assistant-role text. Turn receipts therefore are **not cryptographic proof of model output or authority to change CRM data**. The HTTP AI route validates the request and persisted user text; raw finish is not an HTTP endpoint. SQL ownership, typed validation, version checks, and the reviewed action path remain independent boundaries. Proposal hashes identify content; they are not secret capabilities.

### Thread and Turn Integration

- `GET /api/conversations`: recover the owner's expired turns, then list threads.
- `POST /api/conversations`: new thread with `{epoch, version, title}`.
- `POST /api/conversations/switch`: switch with `{epoch, version, threadId}`.
- Existing `GET/PUT /api/conversation`: active history/state contract remains; reads support the active-epoch guard and paging.
- `POST /api/pipechat-ai`: the browser first flushes the user message, then supplies stable `turn: {threadId, requestId, userMessageId, assistantMessageId}` and `conversation: {epoch, version}`.
- `GET /api/conversations/:threadId/turns/:requestId`: retrieve the durable result; retry lookup does not dispatch another planning run.

Begin claims the accepted turn once. Finish persists terminal status, the stable assistant message, and the bounded result receipt in the originating active or archived thread without replacing current focus/state. A disconnected browser does not cancel the server's finish attempt. Process loss is different: expired pending turns become `interrupted` on an authenticated recovery/read, **without rerunning the model**. A revoked session or unavailable database can defer persistence until the owner returns and recovery succeeds.

The durable request ID also identifies usage reservation and request/model telemetry. One claimed planning run can still include primary, review, or repair model calls. Turn completion, quota settlement, and request/model telemetry are separate transactions; do not describe them as exactly-once external execution or atomic billing. New-thread creation itself uses epoch/version conflict detection, not a separate idempotency key.

### Rollback Compatibility

- Prefer a forward fix. Stop new writes and preserve current data before any incompatible rollback. Keep migrations, archives, journals, workflow event tombstones, grants, and usage receipts; there is no supported destructive down migration in this release.
- An older application may still call compatible legacy RPC signatures, but this is not full behavioral compatibility. It may omit journaling, strip new metadata, or be unaware that 016 executes workflows. Test the specific rollback artifact against a restored private copy before enabling its writes.
- Do not restore old function definitions over 016 wrappers, remove 018 to make readiness green, or reset conversations to recover the UI. An old pending confirmation must never become valid merely because the application was rolled back.
- Local JSON mode retains legacy active fields plus a thread catalog. An older writer that drops unknown fields can destroy that catalog. Do not run it against upgraded conversation files. JSON locking is process-local, not a distributed multi-writer guarantee.
- Database snapshot restoration is a separate recovery operation, not an application rollback: it can lose post-backup writes and needs explicit reconciliation. Never switch to JSON as an automatic cloud-failure fallback.

## Known Limitations

- The proposal export is `text/html; charset=utf-8`, with a safe `.html` filename, escaped values, and restrictive content policy. It is printable, not a native PDF service, permanent hosted artifact store, e-signature, email delivery, or share link. Deal Value is not silently promoted into contractual price/currency; missing terms remain `Unknown`.
- Workflows create a task **at the qualifying transition**, with its due date anchored to that event's local calendar date. They are not a delayed scheduler, external notification system, arbitrary script engine, or general-purpose automation language. Only saved failed events are retryable; consumed identities must survive undo/task deletion.
- Hosted graph/sharing and durable workflow HTTP routes require Supabase. Pure module tests and local JSON conversation support do not establish equivalent local graph/workflow persistence.
- Graph schema evolution is additive under its current contract. Graph audit, legacy CRM undo, dashboard state, conversation state, and sharing are not one universal undo transaction. Do not promise every operation can be reversed.
- Expired-turn recovery is owner-authenticated and on access, not an always-running cross-user worker. Legacy requests without turn metadata do not acquire retroactive receipts. Large histories and bounded payload rejection need scale testing; no automatic retention/compaction policy for all ledgers is claimed.
- Tokens are recorded when actually reported by the provider. Unknown usage/cost stays unknown; no invented pricing. Journal event `latencyMs: 0` is unmeasured, not a performance result. Complete activation, retention, and product analytics coverage is not certified by the event ledger alone.
- Offline regression and embedded PostgreSQL tests do not certify live Auth/PostgREST, independent database-connection races, browser/model interpretation, delivery, or production recovery. Transparent unsupported responses are safer than fabricated success, but still leave the requested objective unmet.

## Connected-AI Acceptance Protocol

**R lane: `test@test`, read-only or preview-and-cancel only.** Never Apply, Confirm, Yes-to-save, Undo, reset, import-commit, change graphs, activate workflows, grant access, or send invitations. Querying can consume quota and persist chat/telemetry; this is read-only business acceptance, not a promise of zero database writes. A safe document download may be inspected locally but must not be distributed. Stop and record any unexpected mutation. Do not compensate by making another unapproved write.

**Q lane: separately authorized disposable QA accounts/workspaces.** All commits, undo, new/switch-thread recovery drills, sharing, fault injection, expiry, and concurrency tests belong here. Use two approved identities for isolation, and separate owner/viewer/editor cases. No real recipients or live customer records. Do not alter the production clock or authentication configuration for a test.

Capture a canonical before snapshot, IDs, versions, timezone, configured models, deployment revision, and allowance before each scenario. Confirm only the reviewed fixture plan; compare persisted deltas, refresh, query again, and replay the same request/action/import/event ID where applicable. Verify no duplicate writes or charges, and preserve evidence of any discrepancy. Restore only QA fixtures with a reviewed inverse or approved fixture teardown. Cancellation must leave business state unchanged, even though chat/quota history can change.

Historical numbers are conditional oracles, not current facts: the report's 42-record fixture totaled $1,624,800; its Ravi subset was 3/$161,000/$53,666.67. Use these only with a verified matching fixture. Otherwise independently calculate the current expected answer. Do not reconstruct a full dataset from a partial report. For relative dates record the actual app date/timezone; a controlled QA clock at 2026-10-10 gives two weeks = 2026-10-24 and seven days = 2026-10-17. Literal dates in pasted material remain literal.

Every row requires the requested outcome, not just a plausible reply. Save redacted request/plan/action/turn IDs, preview and read-back evidence, artifact metadata where relevant, actual versus expected results, and an issue reference. A `None` response, generic failure, invented fact, omitted subrequest, or unsupported requested outcome is not a pass. Mark individual cases **Pass / Fail / Blocked** only after execution; the checkpoint above and private evidence files track the incomplete live run.
